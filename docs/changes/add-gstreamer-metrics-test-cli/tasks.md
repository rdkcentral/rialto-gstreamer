## 3. Fault Injection
Faults are injected with a pad probe on the `rialtomsevideosink` sink pad, so the CLI never calls `notifyMetric` or synthesizes a `media-pipeline-metric` message. Each scenario is selected with `--fault-scenario NAME`, installs its probe only after playback is running, applies it for a bounded window, then removes the probe. A selected scenario that is not implemented keeps failing (see 1.1) rather than running without a fault.

- [x] 3.1 Add the fault-injection framework and register the four scenario names `frame-drop`, `frame-repeat`, `buffer-underflow`, and `decoder-error`. Reject unknown names with the argument-error exit code. Install the sink-pad probe only after the pipeline reaches PLAYING, bound it in time and in the number of affected buffers, and remove it on completion, error, EOS, or timeout. Expose the per-scenario parameters as optional CLI arguments with documented defaults.
- [x] 3.2 Implement `frame-drop` (late frames). In the probe, rewrite the PTS (and DTS, where set) of a bounded number of consecutive video buffers so each lands behind the current playback position and misses its presentation deadline. Start only after playback has settled. Do not use seeks, flushes, or EOS, because those are excluded from the drop definition. Query the current position to compute the offset, and fail with a clear message if it cannot be obtained.
- [x] 3.3 Implement `frame-repeat` (single delayed buffer). In the probe, hold one video buffer for a configurable number of frame durations (default: 3), then release it so the renderer repeats the preceding frame. Derive the frame duration from the framerate caps or the buffer duration, and fail with a clear message if neither is available. Keep the delay below the underflow threshold, and do not rely on 3:2 or 2:2 cadence, which is excluded from the repeat definition.
- [x] 3.4 Implement `buffer-underflow` (decoder input starvation). In the probe, block video buffers from reaching the sink for a configurable duration, then release them so the starvation ends and the resolving half of the pair can be observed. Hold video only, so audio keeps flowing. Choose a duration long enough to drain the decoder input rather than only the client queue, and make it configurable per target. This is independent of need-data flow control.
- [ ] 3.5 Implement `decoder-error` (frame-level corruption). In the probe, map a configurable number of video buffers writable (default: 3) and corrupt the slice payload, leaving SPS/PPS and NAL headers intact so the decoder reports per-frame errors rather than failing the stream. Fail with a clear message for content where corruption is not possible (for example encrypted media). Count the affected frames precisely, because the definition is one error per affected frame.
- [ ] 3.6 Print the injected fault parameters for every scenario (scenario name, buffers affected, offset, delay, or duration applied) so a target run can be correlated with the metric messages observed in section 4.
- [ ] 3.7 Add focused tests for the probe logic that do not need a Rialto server. For each scenario, cover that selected buffers are retimed, delayed, held, or corrupted as configured, that unselected buffers pass through unchanged, and that the probe is removed after its bounded window. Cover failure reporting for missing position, missing frame duration, and non-writable or encrypted buffers.

Messages beyond the first valid one are reported, not treated as failures, because the scenarios overlap (a delayed buffer can cause a drop as well as a repeat, and a long stall can cause a repeat as well as an underflow).
